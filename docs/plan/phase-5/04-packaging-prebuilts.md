# 04 — Packaging: prebuilt per-OS binaries

## Purpose

This feature is what makes the roadmap promise true: **a new user installs with `npm i tekno`, no Rust toolchain required.** The native engine is a `napi-rs` addon that owns the `cpal` thread ([architecture.md](../../architecture.md#the-bridge-ts--rust)); building it from source needs `cargo` and a C toolchain, which no end user should have to install. `napi-rs` is chosen specifically because it [supports prebuilt per-OS binaries](../../architecture.md#why-these-technology-choices) — so we build the addon once per platform in CI, publish those prebuilds, and the `tekno` package pulls the right one at install time with **zero** native compilation on the user's machine.

The mechanism is `napi-rs`'s standard one: a per-platform npm package (`@tekno/engine-<platform>`) for each target, listed as **optionalDependencies** of the main package, plus a small loader that `require`s the matching one. The Rust toolchain becomes a **contributor-only** concern (source build as a fallback). External CLIs `yt-dlp`/`ffmpeg` are handled separately: they are **optional**, checked-for at runtime (only when a sampling path needs them), never bundled, never required to install or play.

## Location

```
bindings/native/
  package.json           # the @tekno/engine root: napi config + optionalDependencies
  Cargo.toml             # the napi-rs crate (engine bindings)
  src/lib.rs             # the addon (start/stop/pushEvents/stats/listDevices/startOffline)
  npm/                   # per-platform stub packages generated by `napi create-npm-dirs`
    darwin-x64/package.json
    darwin-arm64/package.json
    linux-x64-gnu/package.json
    linux-arm64-gnu/package.json
    win32-x64-msvc/package.json
  index.js               # the loader: require the matching @tekno/engine-<platform>
  index.d.ts             # generated TS types for the addon
packages/tekno/
  package.json           # depends on @tekno/engine (the loader package)
  src/engine.ts          # createNativeEngine() → wraps the loaded addon
.github/workflows/
  build.yml              # NEW — the build matrix + publish job
```

This uses the `napi-rs` CLI (`@napi-rs/cli`) conventions, so most of `npm/` and `index.js` are generated, not hand-written.

## Design

### Targets (the build matrix)

The five platforms the roadmap commits to ([cross-platform parity](../../roadmap.md#risks)):

| Platform | Rust target triple | npm package | Artifact (the `.node`) |
| --- | --- | --- | --- |
| macOS x64 | `x86_64-apple-darwin` | `@tekno/engine-darwin-x64` | `engine.darwin-x64.node` |
| macOS arm64 | `aarch64-apple-darwin` | `@tekno/engine-darwin-arm64` | `engine.darwin-arm64.node` |
| Linux x64 | `x86_64-unknown-linux-gnu` | `@tekno/engine-linux-x64-gnu` | `engine.linux-x64-gnu.node` |
| Linux arm64 | `aarch64-unknown-linux-gnu` | `@tekno/engine-linux-arm64-gnu` | `engine.linux-arm64-gnu.node` |
| Windows x64 | `x86_64-pc-windows-msvc` | `@tekno/engine-win32-x64-msvc` | `engine.win32-x64-msvc.node` |

Artifact names follow `napi-rs`'s `<name>.<platform>.node` convention so the generated loader resolves them automatically. (musl Linux and Windows arm64 can be added later by extending the matrix; nothing else changes.)

### The optionalDependencies + loader pattern

The root binding package declares each per-platform package as an **optional** dependency with `os`/`cpu` constraints. npm installs only the one matching the user's platform; the others are skipped (their `os`/`cpu` don't match), so the user downloads exactly one prebuilt binary.

```jsonc
// bindings/native/package.json  (the @tekno/engine loader package)
{
  "name": "@tekno/engine",
  "version": "0.5.0",
  "main": "index.js",
  "types": "index.d.ts",
  "napi": {
    "name": "engine",
    "triples": {
      "additional": [
        "aarch64-apple-darwin",
        "aarch64-unknown-linux-gnu",
        "x86_64-pc-windows-msvc"
      ]
    }
  },
  "optionalDependencies": {
    "@tekno/engine-darwin-x64":      "0.5.0",
    "@tekno/engine-darwin-arm64":    "0.5.0",
    "@tekno/engine-linux-x64-gnu":   "0.5.0",
    "@tekno/engine-linux-arm64-gnu": "0.5.0",
    "@tekno/engine-win32-x64-msvc":  "0.5.0"
  },
  "devDependencies": { "@napi-rs/cli": "^2" },
  "scripts": {
    "build": "napi build --platform --release",
    "build:debug": "napi build --platform"
  }
}
```

```jsonc
// bindings/native/npm/darwin-arm64/package.json  (one per platform; generated)
{
  "name": "@tekno/engine-darwin-arm64",
  "version": "0.5.0",
  "os":  ["darwin"],
  "cpu": ["arm64"],
  "main": "engine.darwin-arm64.node",
  "files": ["engine.darwin-arm64.node"]
}
```

The loader (generated by `napi-rs`) picks the right binary at require-time:

```js
// bindings/native/index.js  (shape of the napi-rs-generated loader, abridged)
const { platform, arch } = process;
function load() {
  // 1) Local dev: a freshly source-built binary next to this file.
  try { return require(`./engine.${platform}-${arch}.node`); } catch {}
  // 2) Installed prebuilt: the matching optional dependency.
  switch (`${platform}-${arch}`) {
    case "darwin-arm64": return require("@tekno/engine-darwin-arm64");
    case "darwin-x64":   return require("@tekno/engine-darwin-x64");
    case "linux-x64":    return require("@tekno/engine-linux-x64-gnu");
    case "linux-arm64":  return require("@tekno/engine-linux-arm64-gnu");
    case "win32-x64":    return require("@tekno/engine-win32-x64-msvc");
  }
  throw new Error(
    `tekno: no prebuilt engine for ${platform}-${arch}. ` +
    `Build from source: see docs/guide/troubleshooting.md (needs the Rust toolchain).`
  );
}
module.exports = load();
```

`packages/tekno` depends on `@tekno/engine`, and `src/engine.ts`'s `createNativeEngine()` simply wraps the loaded addon — the rest of the library only ever sees the [`Engine` interface](../../event-protocol.md#control-call-surface-non-real-time), so swapping the WASM backend later ([Phase 6](../../roadmap.md#phase-6--web-backend-later)) changes nothing above this point.

### CI build matrix (in `.github/workflows/build.yml`)

One job per target builds the `.node`, runs the test suite, and uploads the artifact. A final job assembles the per-platform npm packages and publishes them (plus the loader and `tekno` itself) on a tagged release.

```yaml
# .github/workflows/build.yml  (sketch)
name: build
on: [push, pull_request]

jobs:
  build:
    strategy:
      fail-fast: false
      matrix:
        include:
          - host: macos-latest    target: x86_64-apple-darwin
          - host: macos-latest    target: aarch64-apple-darwin
          - host: ubuntu-latest   target: x86_64-unknown-linux-gnu
          - host: ubuntu-latest   target: aarch64-unknown-linux-gnu   # cross-compile
          - host: windows-latest  target: x86_64-pc-windows-msvc
    runs-on: ${{ matrix.host }}
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable
        with: { targets: "${{ matrix.target }}" }
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: npm ci
      - run: npx napi build --platform --release --target ${{ matrix.target }}
        working-directory: bindings/native
      - run: npm test          # pure-TS + native smoke test where the host can run it
      - uses: actions/upload-artifact@v4
        with:
          name: engine-${{ matrix.target }}
          path: bindings/native/engine.*.node

  publish:
    needs: build
    if: startsWith(github.ref, 'refs/tags/v')
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/download-artifact@v4     # gather all engine.*.node
      - uses: actions/setup-node@v4
        with: { node-version: 20, registry-url: "https://registry.npmjs.org" }
      - run: npx napi prepublish -t npm        # places each .node into its npm/<platform> dir
        working-directory: bindings/native
      - run: npm publish --access public --workspaces   # @tekno/engine-* + @tekno/engine + tekno
        env: { NODE_AUTH_TOKEN: "${{ secrets.NPM_TOKEN }}" }
```

`napi prepublish` is the `napi-rs` CLI step that copies each built `.node` into its `npm/<platform>/` stub and rewrites versions, so `npm publish --workspaces` ships every per-platform package alongside the loader and the main `tekno` package. The user-facing `npm i tekno` then resolves exactly one `@tekno/engine-*` prebuild via the `os`/`cpu` constraints — no compilation.

### Fallback: source build for contributors

A contributor on an unlisted platform, or one hacking on the engine, builds from source:

```bash
# from bindings/native/
npm run build         # napi build --platform --release  → engine.<platform>.node next to index.js
```

The loader's step (1) above prefers that locally-built `.node`, so a source build "just works" without touching the optional dependencies. The error thrown when no prebuilt and no local binary exists points the user at [troubleshooting](07-getting-started-docs.md) with the source-build instructions. `npm i` for an end user never triggers a source build (no `install`/`postinstall` compile step), so a missing Rust toolchain is never fatal for users — only the (clearly messaged) unlisted-platform case is, and that is the contributor path.

### Optional external CLIs: `yt-dlp`/`ffmpeg`

These are **not** npm packages and are **never bundled**. They are needed only by the [Phase 4 YouTube ingest](../phase-4/00-overview.md) (`sample.fromYouTube`), which is itself opt-in ([roadmap.md](../../roadmap.md#risks)). The packaging contract:

- **No install-time dependency.** `npm i tekno` neither installs nor checks for them. Playback, the synth/drum voices, and local-file sampling all work without them.
- **Lazy runtime check.** The first time a song calls `sample.fromYouTube(...)`, the sampler runs a one-time presence check (`yt-dlp --version`, `ffmpeg -version` on the PATH). If either is missing, it throws a clear, actionable error naming the missing tool and pointing at [docs/guide/sampling.md](07-getting-started-docs.md) (with the install hint per OS and the copyright/ToS note) — it does **not** crash the engine.
- **`tekno doctor` (optional convenience).** A small CLI subcommand can report which optional tools are present, so users can verify their sampling setup before a session. (Implementation is trivial atop the same presence check; listed here so packaging owns the contract.)

```ts
// shape of the lazy check (in the Phase 4 sampler, contract owned here)
async function requireExternal(tool: "yt-dlp" | "ffmpeg") {
  if (!(await onPath(tool)))
    throw new Error(
      `tekno: "${tool}" is required for YouTube sampling but was not found on PATH.\n` +
      `Install it (see docs/guide/sampling.md) — note YouTube sampling is opt-in and ` +
      `subject to copyright/ToS. Local files need no extra tools.`
    );
}
```

## Interfaces

- **To [packages/tekno](01-hot-reload-runtime.md):** `src/engine.ts` `createNativeEngine()` wraps `require("@tekno/engine")`; everything above sees only the [`Engine` interface](../../event-protocol.md#control-call-surface-non-real-time) (`start`/`stop`/`pushEvents`/`stats`, plus `startOffline`/`listDevices` added in [02](02-cli.md)).
- **To the [napi bridge](../phase-0/04-napi-bridge.md):** this packages the exact addon that bridge defines; no API change, only distribution.
- **To [Phase 4 sampling](../phase-4/00-overview.md):** owns the optional-CLI presence-check contract; the sampler imports and calls it.
- **To [Phase 6](../../roadmap.md#phase-6--web-backend-later):** the loader indirection means the web (WASM) `Engine` implementation slots in without any change to song code or the library above `engine.ts`.
- **To the user's workflow:** `npm i tekno` → ready to `tekno play`. No `cargo`, no `node-gyp`, no `yt-dlp`/`ffmpeg` unless they opt into YouTube sampling.

## Edge cases & risks

- **Unsupported platform.** If no `@tekno/engine-*` matches (e.g. musl Linux, Windows arm64 before the matrix grows), the loader throws a clear error pointing at the source-build path — never a cryptic `MODULE_NOT_FOUND`.
- **Version skew between loader and prebuilt.** All per-platform packages and the loader are published from the **same** CI run at the **same** version, pinned exactly (`"0.5.0"`, not `^`), so a user can never get a mismatched engine ABI. `prepublish` enforces version sync.
- **optionalDependencies install hiccups.** If a registry/network blip skips the optional dependency, the loader's local-binary step still fails clearly; the fix (reinstall, or build from source) is documented. We do **not** fall back to a `postinstall` compile, to keep "no Rust toolchain" inviolable.
- **macOS Gatekeeper / code signing.** Prebuilt `.node` files loaded by Node are not Gatekeeper-quarantined the way `.app`s are, but we note codesigning/notarization as a follow-up if distribution ever moves outside npm. Within `npm i`, the binary is trusted as a normal package file.
- **External CLIs absent.** Covered above: lazy check, clear error, never fatal to playback. `ffmpeg`/`yt-dlp` version differences are tolerated (we only invoke documented, stable flags).
- **Cross-compiled Linux arm64.** Built via cross toolchain in CI; smoke-tested on an arm64 runner/emulator before a release is cut, per the [cross-platform DoD](../../roadmap.md#cross-cutting-definition-of-done-every-phase).
- **Binary size in the npm tarball.** Each per-platform package ships only its own `.node` (via `files`), so a user downloads one binary, not five.

## Acceptance criteria

- [ ] **`npm i tekno` installs with no Rust toolchain.** On a machine with **no** `cargo`/`rustc`, `npm i tekno` succeeds and `tekno play examples/hello-kick.ts` makes sound. *How to test:* a CI job in a container without the Rust toolchain installs the published (or `npm pack`-ed) package and runs a headless playback smoke test on each of the five platforms.
- [ ] **Correct prebuild selected per platform.** On each OS/arch, exactly the matching `@tekno/engine-*` is installed and loaded. *How to test:* assert `require.resolve("@tekno/engine-<platform>")` succeeds and the others are absent; assert the loaded addon reports its target.
- [ ] **Source-build fallback works for contributors.** `npm run build` in `bindings/native/` on a dev machine produces a `.node` the loader picks up, with no published prebuilt present. *How to test:* CI contributor job builds from source and runs the same smoke test.
- [ ] **Unsupported platform fails clearly.** The loader's error names the platform and points at the source-build docs. *How to test:* unit test the loader with a stubbed `process.platform`/`arch` not in the matrix.
- [ ] **Optional CLIs are truly optional.** Playback and local-file sampling work with `yt-dlp`/`ffmpeg` absent; `fromYouTube` throws the documented actionable error (not a crash) when they're missing. *How to test:* run the [hip-hop example](03-example-songs.md) (local asset) in a CI env with both tools removed; assert it plays; assert the `fromYouTube` path errors cleanly.
- [ ] **Versions are locked in lockstep.** Loader and all prebuilds share the exact version from one CI publish. *How to test:* a release check asserting version equality across all `@tekno/engine-*` + `@tekno/engine` + `tekno`.
- [ ] **Cross-platform.** Install + play verified on macOS (x64/arm64), Linux (x64/arm64), Windows (x64) in CI before sign-off.
